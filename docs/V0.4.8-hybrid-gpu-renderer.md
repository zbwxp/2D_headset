# V0.4.8 — Hybrid GPU Main 2D Renderer

## Scope and architecture

Production Main 2D now uses `GpuDerivedRenderer`; Semantic Geometry remains CPU/TypeScript. Existing 3D Inspector, Contour Worker, source geometry, Smooth, View Lock, placement, history and picking are not rewritten.

DOM order: reference image/background SVG → transparent WebGL Canvas → SVG InteractionOverlay → UI controls. Canvas has `pointer-events:none`. Reference images remain DOM images. Points, ON_CURVE points, exact selected Curve highlights, Bézier handles, guides, labels and hit targets stay SVG.

`DerivedRenderLayer` integrates the existing frame-coalesced project snapshot and Smooth result notifications. `editRenderSnapshot` packs final BasePatch + Fullness + optional evaluated Smooth. Renderer inputs remain only `EditRenderSnapshot`, `OrthographicViewState`, `EditRenderStyle`. There are no Patch/placement/solver calls in the GPU renderer.

## Resources and lifecycle

`GpuDerivedRenderer` creates one persistent Three.js WebGLRenderer per mount, with alpha, antialias and stencil enabled. A single pending RAF draws the latest props; there is no idle animation loop. Canvas DPR/size changes update the drawing buffer. Unmount cancels RAF, disposes all geometries/materials/context and removes listeners. Context loss produces a clear warning; restoration schedules a redraw. Initialization failure reports an error rather than silently running CPU and GPU together.

`GpuScene` owns the independent scenes, materials, camera and ID-to-resource maps:

- Surface ID → geometryToken, one BufferGeometry shared by depth/color meshes.
- Curve ID → geometryToken, one LineGeometry shared by x-ray/front Line2 objects.
- Unchanged ID + token reuses resources; changed entities replace only their geometry; deleted entities are disposed.
- Selection only changes object visibility. Opacity changes uniforms/material state. Camera changes matrices. These operations do not upload unchanged geometry.
- Area-weighted normals are packed and cached in the render adapter with each changed final mesh, never recomputed per camera frame.

The development upload counters count entity buffer replacement and expected buffer byte volume, not GPU timer-query time. `gpuDrawSubmission` measures CPU command submission, not GPU completion.

## Four GPU passes

1. **Surface depth:** all final triangles; double-sided, depth test/write on, color off.
2. **Surface color:** depth test on, depth write off, simple normal-based shading; alpha 50/75/100%. A stencil mark on successful nearest-depth samples prevents coincident surfaces blending a second time. No transparency sorting/OIT/layer accumulation.
3. **Ordinary Curve X-Ray:** depth test/write off, opacity 25%.
4. **Ordinary Curve front:** same ribbons, depth test on/write off, opacity 100%.

Selected curves are excluded from both ordinary passes and highlighted by SVG. A tiny curve clip-depth bias (`1e-7`, equivalent to 0.0001 world units at the shared depth range) plus surface polygon offset (factor 1, units 1) stabilizes boundary display. No source positions move.

## Projection and AA

GPU directly uses the shared `viewMatrix` and `projectionMatrix`; no second camera convention. V0.4.7's XY mapping was correct, but its view matrix had a reversed Z row. V0.4.8 corrects that row to the observer-facing camera +Z basis and adds tests for matrix handedness and near-before-far depth. XY projection, SVG coordinates and geometric constraints do not change.

Line2/LineGeometry/LineMaterial draw triangle ribbons, not native GL wide lines. Width is 1.5 CSS pixels. DPR-aware framebuffer and default-canvas MSAA cover surface/ribbon edges; derivative-smoothed line caps improve AA without alpha-to-coverage applying an extra coverage multiplier to the 25% x-ray alpha. No offscreen target or postprocessing pipeline is used this version.

Low display quality still has the same coarse tessellation geometry as before. MSAA reduces pixel aliasing, not the polygonal silhouette caused by intentionally low subdivisions.

## CPU reference and future extension

Development only: `?renderer=cpu` opts into the CPU/SVG logical reference; default or `?renderer=gpu` runs GPU exclusively. Production ignores the CPU option. CPU reference tests explicitly opt in. Main GPU runs zero CPU curve occlusion and creates zero SVG surface triangles.

`GpuScene` separates resources/scenes from the visible-canvas React lifecycle. A future offscreen renderer can consume the same final buffers and scene resources within its own WebGL context. GPU objects cannot be shared across separate WebGL contexts; typed final buffers can. No GPU Contour or GPU picking is implemented now.

## Verification and performance

See `tests/e2e/gpu-renderer.spec.ts`, `gpu-performance.spec.ts` and `src/tests/gpu-renderer.test.ts`.

Actual GPU compositor pixel checks cover Front/45°/Side at DPR 1 and 2: nearest-only 75% alpha remains 191/255 even with overlapping and coincident surfaces; front and boundary curves have matching strong coverage, hidden curves retain x-ray coverage. Pixel reads occur only in test code through a Canvas2D copy, never in production picking.

Projection unit tests cover DPR 1/2/3, multiple aspect ratios and pan/zoom; browser tests cover actual canvas dimensions, selection and no-upload camera updates. Screenshot files are under `artifacts/gpu-renderer/`.

Performance uses the same 51-point / 77-curve / 30-patch real HeadShell at medium display quality, 1600×1050 CSS, DPR 2, 3D visible. CPU reference and GPU run the same workloads. A/B/C: 60 Fullness updates, respectively Smooth OFF, Smooth ON, Smooth+Contour ON. D: actual boundary Curve handle pointer drag. E: 60 Main 2D pan/zoom updates. RAF intervals measure interactive main-thread cadence, not a promised device-independent FPS. Existing Smooth edit-session policy is retained; post-release settling is recorded separately.

| B — 60 Fullness edits, Smooth ON | 8.556 s | 1.339 s | 216.7 ms | 33.4 ms |
| C — 60 Fullness edits, Smooth + Contour ON | 9.241 s | 1.612 s | 233.4 ms | 50.0 ms |
| D — 40 real handle pointer samples | 9.949 s | 2.410 s | 133.3 ms | 33.3 ms |
| E — 60 pan/zoom changes | 6.453 s | 1.083 s | 166.7 ms | 33.3 ms |

D uses the actual handle of 左面壳前边界·额颞至颧颊 in Right45. Assertions require >20 source updates and affected patches; the ineffective early attempt on an offscreen/edge-on handle was discarded. Pointer scenario timings include browser input and deliberate 16 ms pacing, so they are interaction comparisons, not kernel benchmarks.

GPU A uploaded exactly 120 patch buffers (2 affected patches × 60 edits), zero curves. E uploaded zero Surface/Curve buffers, did zero patch tessellation, zero 3D buffer rebuild and zero Smooth dispatch. Every GPU scenario had zero CPU occlusion candidates and zero SVG surface triangle paths. B/C can update more than two final buffers when a global Smooth result arrives; source incremental work remains unchanged.

Per interaction, GPU draw submission totaled approximately 17–31 ms. Remaining inclusive geometry/read/React-associated evaluation timings were approximately 347–751 ms, and 3D updates 65–187 ms. These timing scopes overlap and must not be summed. C had a 33.2 ms median RAF interval versus 16.7 ms in GPU A/B/D/E: Smooth/Contour/CPU work still matters. Post-release settling B/C was observed at roughly 1 second, but this includes polling granularity and a fixed 100 ms test buffer; it is not an exact solver duration. No remaining solver was rewritten in this version.

Raw counters/timings: `artifacts/gpu-renderer/performance-{cpu,gpu}.json`.

### High-detail depth/color regression

Manual DPR1 high-zoom inspection found speckled missing color. A real high-subdivision head coverage comparison reproduced 714 missing interior pixels. The color vertex shader multiplied projection and modelView matrices before applying the vertex, whereas the depth material applied modelView to the vertex first. Matching the depth pass operation order fixed the numerical mismatch; the strict <5 missing-pixel regression passes. This is a rendering-only fix, without geometry displacement, lower quality or large depth offsets.
