# 16 成品形态、共用求值核心、未来能力的检查场景（v0.2，2026-10-06）

> 来源：bowen 与 dot 在 #headset-collab 的讨论（2026-10-06）。Claude 整理入库，dot 审。
> 本文件只写**需求和检查场景**。表情和捏脸怎样组合、用什么算法，**没有定**；“再叠一层偏移”只是候选之一，不是原则，也没有“通用变形层”的全局概念。
> v0.2（dot 审）：§1 输入要包含可解析的部件、规则和资源依赖；新增 §1.1 共同接口；§3 两种程序都测局部和全量；§5 统一推进顺序。

## 1. 成品是什么

最终成品是**捏脸器**：用户捏出自己的角色，并且随时预览、播放这张脸的表情和转头。我们现在做的是**制作这个捏脸器的工具（制作器）**。

| 程序 | 做什么 | 不需要什么 |
| --- | --- | --- |
| 制作器 | 定义线条、可捏参数、表情、转头，以及它们怎样组合 | — |
| 捏脸器 | 按制作器给出的规则调整、保存用户自己的角色，同时预览表情和转头 | 钢笔、反推编辑、全部制作界面 |
| runtime（播放） | 读取角色和规则，接收角度、表情参数，算出并显示结果 | 编辑、撤销；可以只读制作器导出的精简数据 |

**要求**：三处共用同一套“这张脸怎样被算出来”的核心（角色含义 + 求值规则）。同一角色、同一组参数，三处结果一致。不要求三个程序装同一份全部代码；runtime 可以用精简数据，前提是不丢失约定的效果。目的：以后不会出现一个和制作器解释不同的播放器。

对底座的直接含义：求值核心（`proto/base` 里的 `evaluate` / `derived`）要能脱离编辑器单独运行，输入只有“角色数据 + 参数”，不依赖撤销、事务、界面。“角色数据”必须**自带可解析的部件、规则和资源依赖**，不能暗中仍依赖编辑器状态（例如编辑器里才有的选择、临时预览、未导出的缓存）。

### 1.1 先定共同接口，不预设求值方式

每种能力（转头、表情、捏脸、以后的其他能力）先回答同一组问题，接口要能容纳**不同的求值方式**，不预设都是“加法形变”：

| 问题 | 例子（仅说明含义） |
| --- | --- |
| 输入什么 | 哪份角色数据、哪些参数（角度、表情强度、滑杆值） |
| 依赖哪些对象 | 哪些部件、线、点、规则、资源 |
| 输出什么 | 哪些几何（点、线、填充）和外观（显隐、笔触） |
| 编辑写回哪里 | 改的是部件（共用）、角色（只影响自己），还是某条规则 |

注意：**参数值怎样混合**（如 Live2D 表情对参数的 Add / Multiply / Overwrite）和**几何怎样组合**不是同一件事；前者不能证明捏脸、转头都能靠偏移叠加解决。

## 2. 未来能力的检查场景（加入底座验证，不等捏脸器做出来）

**场景 E（眼睛）**：同一份眼睛部件，做出**宽眼**、**窄眼**两个角色；两者共用同一套转头和表情。

分别检查：

1. **闭眼**、**惊讶**两个表情，在两个角色上各自的结果符合预期；
2. 改一个角色的眼型，**不会误改**另一个角色，也不会改到共用的部件和表情；
3. 转头之后，捏的形状和表情都还在；
4. 几种修改组合（捏脸 + 表情 + 转头，以及表情之间）的结果符合预期。

底座要能回答（这是检查标准，不是答案）：

- 每种修改**归谁**：部件（所有角色共用）、角色（只影响这个角色）、表情或转头规则；
- 作用在**哪里**：哪些线、哪些点；
- **怎样组合**：先后顺序、组合方式；
- **依赖怎样更新**：改了其中一项，哪些结果要重算。

**没有定、留作比较的**（dot 举的例子）：

- 惊讶时眼睛放大：是在已经捏窄的眼睛上按比例放大，还是朝一个预设的“惊讶形状”靠近？两种结果不同；
- `>_<` 这类表情可能**换线条**，不只是点的位移相加；
- 在 0° 捏的形状，到 30° 怎样保持一致（候选：捏脸偏移也按角度记录 / 捏脸先改底稿、录制相对底稿 / 先变成参数再由参数决定各角度形状）。**这三种候选都还没有验证，不承诺“都走得通”**。

比较方法：用场景 E 逐一试组合方式。普通加法能解决的就用加法；解决不了的，要说明需要的是参数联动、按角度修正，还是形态切换（换线条）。

参考（行为层面）：Live2D 的表情只改“参数值”，叠加方式有 Add / Multiply / Overwrite 三种（官方规范 `CubismSpecs/FileFormats/exp3.json.md`，已核对）；参数值再经各参数的关键形态换算成形状。MMD 的 morph、Blender 的形态键是“相对原形的偏移 × 权重”（按已有了解，未重新核对）。

## 3. 性能：两种工作量，同一个求值核心

| 场景 | 典型工作量 | 要测什么 |
| --- | --- | --- |
| 制作器 | 多角度洋葱皮；一次编辑常常只影响局部，但也可能**整层 / 整稿变化** | 局部和全量都测 |
| 捏脸器 / runtime | 单个画面线条更多；表情、转头常让大部分部件同时变化，但也可能**只调一只眼** | 局部和全量都测 |

局部：工作量是否只随受影响范围增长。全量：吞吐、内存、交互延迟（“局部更新”在全量时帮不上忙；`proto/base` 的测量显示全量时按条目缓存比直接全算慢约 1.5 倍，见 `proto/base/OPEN.md`）。

顺序：两种场景先用**同一求值核心**做规模测试，再决定缓存、后台计算（Worker）或 WASM 的边界。避免只把制作器的小样板优化好。

## 4. 推进顺序（dot 统一，2026-10-06）

1. `375f9e5`（索引、缓存、计数）复验；
2. 贯通一条**真实的拖动预览**增量路径，同时补局部 / 全量规模测试；
3. 用场景 E 比较组合方式（先定 §1.1 的共同接口）；
4. 角度（洋葱皮）缓存。

一次只改一块；不同时改姿态模型、预览和绘制。
