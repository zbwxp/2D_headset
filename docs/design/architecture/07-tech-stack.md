## 1. 路线比较（v0.2：按 dot 的意见把编辑器路线和数据存储分开）

v0.1 把“套 SDK / 自建内核 / CRDT”并列成三条路线，这是错的：CRDT 是存储和同步技术，两种编辑器路线都可能用它。把它们并列，相当于用两个容易排除的选项，制造出“自建必胜”的假象。下面分两层比较。

### 1.1 编辑器路线（三选一）

| 路线 | 做法 | 例子 |
| --- | --- | --- |
| E1 扩展现有编辑器 | 在一个完整编辑器上，通过它的扩展机制（自定义形状、绑定、工具）加入我们的领域 | tldraw SDK |
| E2 复用编辑器子系统，自建领域部分 | 采用能独立使用的画布 / 编辑子系统（选择、命中、变换控件、路径编辑）以及存储子系统，自己写领域部分 | 拆成三个真实组合，见 §1.1.1（dot 核对官方资料与源码） |
| E3 从小型库组装 | 每个子系统都自己组装：补丁、存储、校验、几何、渲染各用一个小库 | Immer + idb + valibot + bezier-js + Clipper2 + Canvas2D |

**三个组合共同的接入边界**（dot 修订）：必须成立的是“**作者数据只有一份权威来源，提交和历史只有一套**”。真正禁止的是两套可以互相覆盖、没有明确归属的原稿。

至于由谁来当这份权威原稿，现在不预先规定，有两种方案都可以比较：
- 库里的对象只做我们文档的投影；
- 现成内核可靠地承载权威几何，再由统一的工程层管理模板和响应。

不能先要求现成内核放弃它原有的编辑模型，等到发现适配很贵时，又因此偏向自建。

**共同检验流程**（以后所有路线都用它来检验；今晚只写接入边界，不做性能实测，也不按速度排名）：
拖动手柄 → 可变线宽描边更新 → 关联的角色更新 → 一次撤销全部恢复 → 保存再打开，结果一致。

**观察**（尚未验证）：

**今晚不做结论**。之后要验证的项目：
- **E1、E2（各组合）、E3 接受同一套实际操作检验**，即 §1.1.1 的共同检验流程：拖柄 → 可变线宽描边更新 → 关联角色更新 → 一次撤销全部恢复 → 保存重开一致。不能只让 E1 做试接，而让 E2、E3 只估工作量。
- 每条路线都记录：哪些步骤由现成部分承担，哪些需要适配或自写，以及遇到的阻碍。
- E1 另需 bowen 判断 tldraw SDK 的许可证能否接受。

### 1.2 数据存储方案（与编辑器路线独立）

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 自己的规范化存储 + 补丁（Immer） | 轻、可控 | 迁移、历史需要自己组装 |
| `@tldraw/store`（MIT） | 记录、差异、迁移都现成 | 发布节奏绑定 tldraw |
| CRDT（Yjs / Loro / Automerge） | 撤销、同步、将来多人协作都现成 | 体积大（Loro / Automerge 的 WASM 约 3.5 MB）；数据类型会渗透到实体；y-indexeddb 自 2023-11 起没有新版本；我们目前是单人使用 |

**当前倾向**：不选 CRDT 作为起点，但要求实体有稳定 ID、修改以实体为粒度，以免将来接入的路被堵死。最终要和编辑器路线一起定。

### 尚无现成实现的部分：分成两类

**A. 已有通用实现，但需要领域适配**（实现方式取决于所选路线）

| 部分 | 现状 |
| --- | --- |
| 门：校验、写入目标解析、提交协议、撤销历史 | 各编辑器 / 存储库都有事务和历史机制；“提交前校验、失败不留步、写入目标可见”需要在其上适配 |
| 求值图：受影响范围、有上限的缓存 | signals / computed 类库可提供失效通知；按实体的计算图与缓存上限需要适配〔未找到现成的 TS 增量计算库，未证实〕 |
| 插件注册表 | E1 有自己的扩展机制；E2 / E3 需要自写，先在进程内注册，接口保持可序列化 |
| 文件格式与迁移 | 校验库和迁移模式（如 tldraw 的迁移序列）可借用，schema 本身需要我们定义 |

**B. 尚未找到可用实现**（今晚的调研范围内；不代表一定不存在）

| 部分 | 已查到的情况 |
| --- | --- |
| 模板 / 角色 / 旋钮 / 规则的数据模型与叠加计算 | 已调研的编辑器和动画运行时都没有“参数驱动的可编辑线稿 + 模板覆盖”的组合 |

| 跨曲线的路径、显隐区间、材质坐标 | 未查到可用实现 |
| 转头插值、反推求解 | 数值求解可用 ml-matrix 等零件，求解问题本身需要我们定义 |

## 3. 目前不倾向的选项及原因（未定）

- **tldraw SDK（E1）**：未定。许可证需要 bowen 判断；数据模型是否合适，要等它和其他路线一样走完共同检验流程才知道（见 §1.1）。
- **CRDT 作数据层**：暂不作为起点。现在用不上协作，却要承担体积和数据模型锁定；但给以后接入留路（见 §1.2）。
- **MobX-State-Tree**：它自己的类型系统和节点身份会渗透到每个实体，锁定程度高。
- **CanvasKit / Vello 作核心渲染**：WASM 约 3 MB，对象模型不同；Vello 没有 JS 包。
- **Live2D、Spine 的代码或格式**：理由以技术需求和集成成本为主（它们是为播放各自模型设计的运行时）。授权条件单列在上表，**不能把授权条件当作排除它们的依据**。

## 4. 主要风险（随路线不同而不同）

1. **不论哪条路线都要自己写的部分**（门的提交协议、规则组合、描边与区间、反推）：工作量和正确性风险都还没有估算。降低风险的办法是让各路线走同一套共同检验流程，再用 RC-01～20 和 N1～N5 验收。
2. **被现成编辑器或子系统锁定**（E1、E2）：被它的发布节奏、许可证、编辑模型绑定；风险大小取决于由谁做权威原稿（见 §1.1.1）。
3. **文件格式**：一开始就带版本号和迁移脚本。
4. **渲染接口**：保持很薄，以便更换渲染后端。
