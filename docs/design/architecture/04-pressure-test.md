# 04 用 RC-01～RC-20 压测候选 A，并修订为 v0.2

版本：v0.2.1（2026-10-06，Claude；吸收 dot 对 v0.2 的 4 条意见，见 §4.1）。输入：[02 候选架构 v0.1](02-candidate-architectures.md)、[03 场景与反例 RC v0.1](03-scenarios.md)。
本文的“建议”都待 bowen 决定。

## 1. 压测结论

v0.1 的大方向成立：统一的文档、只走一套写入接口、作者数据和求值数据分离、只有一条历史。但它在 6 处不够用，v0.2 逐一修订：

| # | v0.1 的问题 | 暴露它的案例 | v0.2 的修订 |
| --- | --- | --- | --- |
| 1 | 默认“一切都是增量”，写入目标只是“哪一层” | RC-05、08、11、12，Q1、Q3 | 引入**贡献（Contribution）**作为一等对象，每个贡献声明归属、作用范围、适用区域、语义、对应要求（§2.2） |
| 2 | L1–L4 四层写死在 base 里 | RC-11、12、14 | base 只强制“组合次序必须显式、确定、可检查”；有哪些阶段由能力注册（§2.3） |
| 3 | 没有变换域 | RC-06、10 | 引入**域（Domain）**：成员规则、继承、与描边分离（§2.6） |
| 4 | 没有有效性状态 | RC-13、15、18 | 求值结果带**有效性**，操作符提交前检查（§2.5） |
| 5 | 材质路径只有一句话 | RC-09 | 引入**路径（Path）**和材质坐标（§2.7） |
| 6 | 只说“可缓存” | RC-20 | 依赖边显式化，按受影响闭包失效，缓存有上限（§2.8） |

另外，我对 dot 的“通用基础必须保证什么”有一处**不同意见**，见 §4。

## 2. 候选 A v0.2 的修订

### 2.1 不变的部分

v0.1 的以下内容保留：①文档存储（不透明的稳定 ID、锚点 ID、谱系）；②事务与历史（一个手势一步，撤销的实现方式不预设，全文档一条历史）；③选择与寻址；⑥保存与导出的区分；⑦几何与外观分离。

### 2.2 贡献（Contribution）：持续参与求值的作者规则

先区分三样东西（dot 的意见，v0.2.1 采纳）：

| 东西 | 例子 | 存在哪里 |
| --- | --- | --- |
| 编辑动作 | 把端点从 x=1 拖到 2，再拖到 3 | 只在撤销历史里，不进求值 |
| 当前作者状态 | 端点现在的坐标 x=3 | 实体自己的字段，原地更新 |
| 持续参与求值的规则 | 30° 的响应修正、角色的局部覆盖、附着约束、域变换 | **贡献** |

贡献只指第三类。**编辑不会自动新增贡献**：修改已有的作者状态或已有的贡献，都是原地更新它的值；只有当一次编辑引入了新的作用（例如第一次在 30° 为某条曲线加修正，或者第一次让某个角色局部覆盖某个锚点）时，才创建一条新的贡献，之后对它的再次编辑仍然是原地更新。

贡献是文档里的普通实体，有稳定 ID，并声明以下字段：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| 归属 owner | 这条贡献属于谁 | 原型部件、某个角色实例 |
| 作用范围 scope | 影响哪些使用者 | 原型（传播给所有后代）/ 仅本角色 |
| 适用区域 region | 在参数空间的哪里生效 | 全域；yaw∈[20°,40°]；表情=笑 |
| 种类 kind | 由哪个能力解释 | 基础几何、参数样本、响应修正、局部覆盖、约束、域变换、来源选择 |
| 语义 semantics | 它表达什么，由创建它的编辑工具显式声明 | 位移 / 目标形状 / 约束（Q1） |
| 组合方式 combine | 和上游结果怎样合成 | 相加 / 替换 / 约束（带优先级） |
| 寻址 targets | 它作用于哪些子元素 | 曲线 ID + 锚点 ID；路径 ID + 材质坐标 |
| 上游 upstream | 修正类贡献依赖哪个上游结果 | “30° 修正”依赖“视角响应”阶段的输出 |
| 阶段 stage | 在组合次序中的位置 | 见 §2.3 |

这样，RC-12 的两种东西就自然区分开了：
- **新增 30° 作者状态** = `kind: 参数样本`，自带内容，上游为空。
- **30° 响应修正** = `kind: 响应修正`，`upstream` 指向视角响应的输出。

两者坐标相同，但种类、上游、归属都不同，序列化后也不会混淆。

注意：组合次序不等于优先级。一条排在后面的“相加”贡献，上游的变化仍然会影响最终结果；只有 `combine: 替换` 或带优先级的约束，才表示“压过上游”。

RC-05 的“局部抬眉”是 `owner: 角色1, scope: 仅本角色, region: 某姿态, kind: 局部覆盖`。原型的修改是另一条 `scope: 原型` 的贡献。两者都参与组合，互不改写。冲突（例如原型删掉了被局部覆盖的锚点）通过 §2.4 的未解决意图来暴露。

### 2.3 组合次序：base 只管“显式”，不管“几层”

- 能力注册**阶段（stage）**，并声明“在哪个阶段之前 / 之后”。base 校验无环、全序、确定，否则拒绝加载。
- 对每个实体求值，就是按阶段次序折叠它的所有贡献。
- 0° 固定、柄优先、尽量少动 90° 这些规则属于“视角响应 / 反向编辑”能力自己（RC-11），不进 base。
- 产品默认的次序（建议，可调整）：

```
来源选择（选哪个变体）→ 原型基础几何 → 域变换 → 捏形参数
→ 视角响应（含姿态分支）→ 表情 → 响应修正 → 角色局部覆盖 → 呈现
```

- 每个阶段的贡献在什么坐标系里表达，由该阶段声明（例如表情在“视角驱动的局部坐标”里表达）。这是 02 §4.3 的难点，仍待实验。

### 2.4 对应关系与未解决意图（RC-02、05、07，Q1）

- 拓扑操作（拆分、合并、删点、换来源）必须产出**对应表**：旧子元素 → 新子元素（或新曲线上的参数区间），材质坐标 → 新材质坐标。
- 贡献按对应表迁移。**无歧义**的部分自动迁移；有歧义或缺失的部分不丢弃，转成**未解决意图**：它是文档里的实体，可以保存、在 UI 里标红、由人工指定新目标或删除。
- 绝不按“最近点”“相近坐标”暗中匹配（RC-02）。

### 2.5 有效性（RC-13、15、18）

有效性按**自由度（分量）**标记，而不是给整个实体一个总开关（dot 的意见：横向压到 0 时，纵向仍然可以移动）。每个可编辑的分量都带一个状态：

| 状态 | 含义 | 编辑时 |
| --- | --- | --- |
| 有效 | 正常 | 可以编辑 |
| 仅正向 | 能显示，但反推没有定义（零缩放、奇异变换） | 拒绝反向拖动并说明原因，提示去编辑源形状或换到非奇异视角（RC-15） |
| 覆盖外 | 请求的参数超出作者数据的覆盖范围 | 显示最近的有效结果，标红只读，**不因为点击就生成作者状态**（RC-13） |
| 未解决 | 有对应缺失的意图 | 显示占位或上一次的结果，并列出未解决项 |

提交协议（RC-18）：预览与提交分离。提交时检查预览所基于的修订号：
- 修订号没变，且预览有效：直接采用预览结果，不重新求解。
- 修订号变了：基于当前修订重新验证。失败则丢弃预览，保留最近一次已提交的结果，并说明原因。
- 任何失败都不留下半次修改，也不产生多余的撤销步。

### 2.6 域（Domain）（RC-06、10）

- 域是一个实体：成员（显式列表或规则，如“该图层的全部曲线”“这条链”）+ 变换参数。
- 后加入的成员按规则自动继承域变换（RC-06：新发丝没有单独形变，但跟随整层透视）。
- 域变换只作用于几何；线宽由呈现能力决定，透视不缩放线宽（RC-10）。
- 重叠的域按阶段次序有序组合，次序是显式数据（待定，见 RC-10）。

### 2.7 路径与材质坐标（RC-09）

- 路径是实体：有序的 `(曲线ID, 方向)` 序列，加上在每个路口**显式选定的分支**。路径可以跨图层。
- 材质坐标定义在路径自己的参数上。显隐区间、收笔、材质区间都寻址到“路径ID + 材质坐标”。
- 塌缩成一点只改变几何长度，不抹掉区间身份；不使用“微小假长度”。
- 曲线被删、分支失效时，路径产生未解决意图，而不是悄悄改道。

### 2.8 依赖与资源界限（RC-20）

- 依赖边从贡献的 `targets` 和 `upstream` 显式推导，不扫描全项目。
- 修改只让受影响闭包失效；缓存键为 `(实体ID, 修订号, 参数坐标)`，有容量上限；逐出缓存不丢作者数据，冷启动结果一致。
- 能力接口禁止要求“每帧复制或哈希整个项目”。
- 验收数值待定。建议用“大库 + 小头部”与“小库 + 小头部”对比，看依赖计算量是否只和受影响闭包有关。

### 2.9 复用三操作（RC-03、04）

| 操作 | 身份 | 与源的关系 | 外部依赖 |
| --- | --- | --- | --- |
| 取引用 TakeReference | 同一身份 | 跟随源 | 不涉及 |
| 独立复制 Copy | 整套重建并重映射内部引用 | 断开 | **必须显式选择**：一并复制，或保留为对外部的引用（复制前展示边界） |
| 移动 Move | 不变 | 迁移成员位置，移除旧位置 | 不涉及 |

“剪切”默认解释为取引用，不是删除。三种操作的语义不从按钮名字推断，而是各是一个独立的操作符。

### 2.10 三种镜像（RC-14）

三个独立的操作符，写入范围互不相交：
- **姿态分支镜像**：按左右对应表，用 +yaw 分支构造 −yaw 分支，写入视角响应的分支贡献，保留稳定身份。非对称部件需要对应表，缺失时产生未解决意图。
- **镜像编辑**：改源几何。
- **相机翻转**：只改观察状态，不写作者数据，不进撤销。

0−/0+ 是否共享几何仍待定。

## 3. 逐条压测（dot 的检查门槛）

“归属 / 写入”指作者数据归谁、这一步写哪里；“次序”指它在组合中的位置；“依赖 / 保存”指影响和保存哪些依赖；“撤销”指撤销后恢复到哪里。

| RC | 归属 / 写入 | 次序 | 依赖 / 保存 | 撤销 | v0.2 状态（设计上可解释 ≠ 已验证） |
| --- | --- | --- | --- | --- | --- |
| 01 改名 | 实体的元数据；不碰几何 | 不参与求值 | 无传播；名称不是地址 | 恢复名称和顺序 | 可解释（标签共享还是局部覆盖待定：Q1） |
| 02 换脸型 | 父项的“来源选择”贡献 | 第一阶段 | 依赖该父项的内容随之重算；附件按锚点 ID 对应 | 恢复来源 | 可解释；B 缺锚点 → 未解决意图 |
| 03 引用 / 副本跨层 | 引用：放置关系；副本：新身份图 | — | 副本的外部依赖边界显式选择 | 各一步 | 可解释 |
| 04 引用 / 复制 / 移动 | 三个独立操作符 | — | 见 §2.9 | 各一步 | 可解释；跨文档引用待定（Q2） |
| 05 原型 vs 局部 | 原型贡献 / 角色局部覆盖 | 局部覆盖在后 | 原型变化传播；局部不反写 | 分别撤销 | 可解释；冲突靠未解决意图暴露 |
| 06 新增发丝跟随域 | 原型基础几何 + 域成员规则 | 域变换阶段 | 新成员自动继承 | 移除曲线与成员关系 | 可解释 |
| 07 拆分后的局部笑容 | 拓扑操作产出对应表 | — | 贡献按对应表迁移；歧义部分成为未解决意图 | 恢复拓扑与贡献 | 细则待设计 需要设计材质坐标的映射规则 |
| 08 两种模式共用编辑器 | 同一批操作符，写入目标由上下文决定并**提交前可见** | — | — | 恢复内容、选择和视图 | 可解释（UI 必须显示写入目标） |
| 09 三岔路径塌成点 | 路径实体 + 区间贡献 | 呈现阶段 | 只影响选中路径 | 恢复路径和区间 | 可解释；方向和端点归属待定 |
| 10 域变换不缩线宽 | 域贡献；线宽由呈现决定 | 域阶段 → 呈现阶段 | 成员按规则 | 恢复 | 可解释；重叠域的次序待定 |
| 11 中间角度不动 0° | 反向编辑能力把手势换算成“响应修正”或“视角响应”贡献 | 视角响应 / 修正阶段 | 0° 固定是该能力的约束 | 恢复作者数据和当时角度 | 可解释；无解时按 §2.5 拒绝并说明 |
| 12 新状态 vs 修正 | 两种不同 kind 的贡献 | 参数样本在视角响应阶段，修正在其后 | 修正依赖上游 | 各自移除 | 可解释 |
| 13 改视图坐标 / 覆盖外 | 视图实体的坐标属性 | — | 覆盖范围重算 | 恢复坐标 | 可解释（覆盖外 = 只读有效性） |
| 14 三种镜像 | 三个操作符 | 姿态分支属于视角响应阶段 | 见 §2.10 | 各一步 | 细则待设计 0−/0+ 接缝和非对称对应待定 |
| 15 零缩放反向拖动 | 不写入 | — | — | 不产生步骤 | 可解释（仅正向有效性） |
| 16 填充与遮挡环 | 呈现贡献 | 呈现阶段 | 全局顺序矛盾检测 | 恢复顺序 | 可解释 v1 只支持全局顺序（Q4） |
| 17 一条撤销历史 | — | — | — | 历史条目记录视图上下文并恢复 | 可解释 |
| 18 预览有效但提交失败 | 提交协议 | — | 修订号栅栏 | 失败不留步 | 可解释 |
| 19 保存后继续传播 | 保存依赖闭包和来源关系 | — | 重开后原型变化仍传播 | 组合编辑可撤销 | 可解释；外部来源升级待定（Q2） |
| 20 大库性能 | — | — | 受影响闭包、有界缓存 | 撤销使缓存失效 | 细则待设计 验收数值待定 |

结论：20 条里 17 条**在设计上可解释**，3 条（07、14、20）结构有了但细则待设计，没有一条需要新增“全局容器”。“可解释”只表示规则层面能回答，**不代表已经通过验证**；性能和数值正确性要等最小实现证明。

## 4. 与 dot 的一处分歧

dot 的“通用基础必须保证什么”最后写道：这些保证不指定必须用实体组件、场景树、命令、快照或不可变文档。

我同意不要过早定**存储表示**（ECS、场景树、不可变文档都可以）。但我认为有两件事必须作为 base 的**结构性决定**写死，否则保证 2（编辑归属）和保证 4（统一事务）无法被强制：

1. **唯一的写入接口**：除了操作符，没有任何代码路径能修改作者数据。能力、UI、AI API 都不例外。
2. **贡献是数据，不是代码**：每个作者修改都以带声明字段的贡献实体存在（§2.2）。这样才能检查它的归属和范围、迁移它、保存它，并在 UI 里显示它。

如果这两点只是“建议”，旧实现里“每个功能自带一套写入和保存”的问题就会重演。

### 4.1 dot 对 v0.2 的意见与处理（v0.2.1）

| # | dot 的意见 | 处理 |
| --- | --- | --- |
| 1 | “唯一写入接口”应表述为：所有已提交作者状态的变更都经过统一的权限、校验和事务入口；撤销、加载已验证文档、批量导入也遵守，但不必重新执行原工具或反解；预览只构造临时候选 | 采纳。分歧消除，叫不叫 operator 是次要的 |
| 2 | 不能把“每次修改都新增贡献”写死，否则编辑过程变成永久求值链（x=1→2→3 只需存 x=3） | 采纳。§2.2 改为区分编辑动作、当前作者状态和持续参与求值的规则，贡献只指第三类，编辑默认原地更新 |
| 3 | “位移能传到新脸型、目标形状不能”太绝对 | 采纳。意图由编辑工具显式声明，用数值例子判定迁移是否正确 |
| 4 | “局部覆盖排最后”不等于总是压过上游；只有替换或约束优先级才表达覆盖 | 采纳。贡献新增 `combine` 字段，次序与优先级分开 |
| 5 | 有效性不宜是整个实体的总开关，同一实体不同分量可编辑性不同 | 采纳。§2.5 改为按自由度标记 |

**待澄清契约**（用具体数值例子判定，不急着新增全局对象种类）：
1. 位移 / 目标形状 / 约束三种意图，在“原型改形”“换脸型”“拆分曲线”三种上游变化下各自应该得到什么结果。
2. 相加 / 替换 / 约束三种组合方式的优先级规则，以及它们和组合次序的关系。
3. 分量级有效性怎样从求值过程推出（例如变换在该方向上是否退化）。

## 5. 对 Q1～Q5 的独立看法

- **Q1 局部意图保留什么**：同意 dot 的建议（每种编辑声明含义；可映射则自动传播，否则保留为未解决意图）。另外建议定默认值：
  - 几何类贡献**必须由编辑工具显式声明**它要保留的意图（位移、目标形状或约束），不靠类型名字推断。位移和目标形状各有用途：位移更容易随脸型变化而传播；目标形状适合“这个角度就要长这样”的美术定稿。迁移正确与否要用具体数值例子来判定（见 §4.1）。
  - 附着关系（耳朵接下颌）是“约束”。
  - “目标形状”只在显式烘焙或导出时出现。
- **Q2 保存与传播**：同意。项目内的原型自动传播；外部库的引用默认**固定版本**，库有更新时提示，由人显式升级（类似 Blender 链接库的重新加载 + 固定）。跨会话撤销建议 v1 不做。
- **Q3 在求值结果上编辑写什么**：每次编辑必须解析到**唯一**的写入目标，由“当前模式 + 当前工具”决定，并在提交前显示（RC-08）。解析不出唯一目标时拒绝并让人选，不猜。
- **Q4 局部交织遮挡**：同意 v1 只做全局顺序、自身边界保护和矛盾检测；局部交织留作呈现能力的扩展。
- **Q5 拖动没有合法含义**：同意拒绝并说明，提供替代路径（编辑源形状、切到有效视角）。永远不自动生成状态，也不用假长度掩盖。
