# 02 候选架构

版本：v0.1（2026-10-06，Claude）。供 dot 用场景和反例压测，最终由 bowen 决定。

## 0. 产品定义（以 dot 的补充为准）

带模板制作器的 OC 线稿生成系统。制作者用曲线做脸、五官等部件，定义它们怎样捏形、转头、做表情；使用者用这些可复用部件组合、调整自己的角色，选择角度和表情，得到**成品级、可继续编辑**的线稿。第一阶段只做头部。制作者和使用者可以是同一个人。

## 1. 旧实现的根本问题（不看代码细节，只看概念）

| 旧概念 | 实际混在一起的东西 |
| --- | --- |
| 图层 | 组织结构、绘制顺序、引用关系、局部状态 |
| 快照 | 参数空间里的关键形态、某个视角的美术修正、存档版本、视口展示状态 |
| 录制 | 插值算法、反推修正、角度绑定、快照组织 |

这三组概念没有共同的数据模型和编辑规则，所以每个组合都要写特例。新架构的第一原则：**一个概念只做一件事，所有概念共享同一套文档、事务、选择、求值和保存规则。**

## 2. 三个候选

### 候选 A：文档存储 + 分层参数 + 求值图（推荐）

参照 Blender（原始数据 / 求值副本 / 操作符）、Figma（扁平存储 / 组件实例覆盖 / 插件只走 API）、Spine 和 Cubism（参数驱动形变、皮肤）。

结构见第 3 节。核心是 base 只提供“存什么、怎么改、怎么算、怎么存”，转头、表情、捏形都是挂在固定参数层上的能力。

- 优点：概念边界清楚；新能力不改 base；保存、撤销、选择天然统一；参数层的作用顺序显式，回答了“改脸型跨视角生效、视角修正不改固有形状”的问题。
- 缺点：前期设计量最大；求值图和覆盖重放需要认真设计；需要规定每一层的坐标系（见 4.3）。

### 候选 B：每个部件一张关键形态网格（Cubism 式）

每个部件在它绑定的参数（yaw、pitch、表情…）上存完整的关键形态网格，配合父子变形器拆维度。

- 优点：心智模型简单，“在哪个角度看到的就是存在哪个关键形态里的”；Cubism 生态证明可行。
- 缺点：维度一多网格就爆炸；中间角度修正要加整行关键点；捏形（角色固有形状）不适合放进网格，只能另做 blend shape，最后还是回到分层。
- 结论：不适合作为 base，但**适合作为候选 A 里“视角层”的一种插值实现**（一个插件）。

### 候选 C：部件 = 元件，状态 = 帧（Flash 式）

每个部件是一个元件，转头和表情是元件里的离散帧，帧之间补间，实例选择当前帧。

- 优点：和旧实现的“快照像帧”最接近，迁移成本最低。
- 缺点：只有一维；多个参数（yaw × pitch × 表情 × 捏形）组合时退化成手工管理的大量帧；捏形没有位置。
- 结论：不适合作为 base。它的“部件定义 + 实例选状态”和“离散切换”两个思想被候选 A 吸收（见 4.4 拓扑切换）。

## 3. 候选 A 的结构

```
┌────────────── 插件（能力）────────────────────────────────┐
│ 视角插值器 · 反推修正 · 捏形面板 · 曲边域 · 导出器 · …        │
│ 只能：注册实体类型 / 操作符 / 求值器 / 面板；只能通过操作符改文档 │
└────────────────────────────────────────────────────────────┘
┌────────────── Base ─────────────────────────────────────────┐
│ ① 文档存储   ② 事务与历史   ③ 选择与寻址                     │
│ ④ 参数层与求值   ⑤ 模板 / 实例 / 覆盖   ⑥ 保存与导出   ⑦ 外观 │
└────────────────────────────────────────────────────────────┘
```

### ① 文档存储

- 文档是扁平的 `实体ID → 实体` 存储。实体有类型（Schema），引用是带类型的 ID 字段，不按名字、不按数组下标。
- ID 由客户端生成，全局唯一且不透明：**ID 字符串里不能编码语义，排序也不能有意义**（旧实现里 ID 字符串顺序决定路径方向和权威节点，是一个已知的坑）。
- 曲线锚点有自己的稳定 ID。插值和对应关系只按 ID，绝不按坐标或角度猜。
- 拆分、合并曲线时记录**谱系**（新曲线由哪条旧曲线的哪一段而来）。之后各层的增量按谱系迁移，而不是指望 ID 不变。
- Schema 有版本号；加载时全量校验，然后才替换当前文档。

### ② 事务与历史

- **所有修改只走操作符**：`操作符(文档, 参数) → 变更`。房间、工具、插件、AI API 用的是同一批操作符。
- 一个用户手势 = 一个事务 = 一个撤销步。拖拽期间修改的是草稿，结束时一次提交，取消则无痕。事务可以嵌套、带名字，只有最外层进历史；没有实际变化的事务不进历史。
- 撤销的实现方式不预设（检验点 1）：可以是前后快照（配合结构共享）、patch，也可以是逆操作。硬性要求只有：可靠；不可逆的变换和退化变换不会因此被禁止。
- 一个文档只有一条历史，不分房间。每个历史条目记录“发生时的上下文”（房间、视口、参数值、选择），撤销时恢复到那个上下文，但**纯导航（改视角、平移缩放、切换选择）不产生撤销步**。〔待 bowen 决定〕
- 每次提交产生一个修订号；“未保存”就是当前修订 ≠ 已保存修订。

### ③ 选择与寻址

- 只有一套选择模型。选择的是**地址**：`(实例路径, 实体ID, 子元素)`，子元素可以是锚点 ID、手柄、区间端点等。
- V / A 只是两种选择深度：V 选部件或编组，A 选曲线和锚点。隔离模式 = 进入部件定义编辑。
- 选择本身不进撤销历史，但撤销时一并恢复。
- 重叠对象的命中规则是 base 的一部分：可循环选择下层对象；锁定对象不吃命中。

### ④ 参数层与求值

视口和导出看到的是“求值结果”，由下面这条固定顺序的管线算出来：

```
部件基础几何（制作者画的中性形）
  → L1 角色固有形状（捏形参数；跨所有视角生效）
  → L2 视角（yaw / pitch；关键形态 + 插值；拓扑切换）
  → L3 表情（表情参数；在视角的局部坐标里叠加）
  → L4 视角美术修正（稀疏增量，挂在某个视角区域上）
  → 外观求值（描边、收笔、显隐区间、填充、遮挡顺序）
  = 求值结果（只读，缓存，永不保存）
```

- 参数是带稳定 ID 的标量（min / default / max），由制作者在部件模板里声明。
- 每一层存的都是**相对上一层的增量**，不存绝对坐标。这样换脸型或改基础形时，上层的制作成果可以沿用（是否“看起来对”另说，见 4.2）。
- **编辑必须指明落在哪一层**（检验点 3）。在 30° 视角下拖一个点，UI 必须明确这是“修改 30° 的美术修正（L4）”，还是“修改角色固有形状（L1，所有角度都会变）”。默认落在哪一层，由当前工具或模式决定，绝不静默改到 L1。
- 反推修正是一个插件：它把用户在中间视角的修改，换算成 L2 关键形态或 L4 修正的增量，再通过操作符写入。base 不关心它用什么算法。
- 求值器（插值器、形变器、外观效果）由插件注册，作用顺序写在 schema 里，确定且可检查。

### ⑤ 模板 / 实例 / 覆盖

- **部件模板**（制作者产物）：基础几何 + 参数声明 + 各层的增量数据 + 外观。
- **角色**（使用者产物）：引用若干部件模板（通过“部件槽”，类似 Spine 皮肤，同一个槽可以换不同的部件），记录参数值和**稀疏覆盖**（按 `(稳定子路径, 属性)` 记录）。
- 三种关系，语义必须区分清楚：
  - **引用**：跟随模板更新。
  - **覆盖**：在引用基础上的局部修改，模板更新后重放；可以“重置覆盖”。
  - **独立复制**：重建整套 ID 和内部引用，与源再无联系。
- 删除被引用的源对象时，引用方必须得到明确的处理结果（阻止、断开成独立副本、或保留占位），不能静默级联删除。

### ⑥ 保存与导出（检验点 2）

- **保存工程** = 序列化文档存储中所选资源的**依赖闭包**（引用的模板、覆盖、资源），不含求值结果。
- **导出结果** = 把当前参数下的求值结果输出成 SVG / PNG / 可再编辑的独立线稿。导出是单向的。
- “把当前求值结果变成一张独立的新线稿继续精修”是一个显式的操作符（相当于 Blender 的 Apply / Illustrator 的扩展外观），产物是一个新的独立对象。
- 写盘是原子的；后台保存捕获的那个修订。

### ⑦ 外观

- 几何与外观分离：线宽、收笔、描边样式、显隐区间、填充都是外观属性，挂在曲线或部件上，跟着部件走，不跟图层位置走。
- 显隐区间和遮挡属于外观求值，作用在求值后的几何上，所以它们可以随视角变化（通过 L2 / L4 给外观属性打关键形态）。
- 图层只负责组织和绘制顺序，**不再承载状态**。

## 4. 需要专门设计的难点

1. **拆分 / 合并曲线后，各层增量怎么迁移**：靠谱系记录。需要定义无法迁移时的行为（阻止编辑，还是丢弃该层增量并提示）。
2. **换脸型复用**：同一套 ID 只保证对应关系，不保证效果合适。需要一个“套用后检查”的流程（Cubism 模型模板的做法：先自动套用，再标出偏差大的地方让人修）。
3. **各层增量的坐标系**：L3 表情和 L4 修正如果存在屏幕坐标里，大角度转头时会错（Cubism blend shape 的已知问题）。建议存在“视角驱动的局部坐标”里，具体选哪种局部坐标需要实验。
4. **拓扑切换**：只有同拓扑才能插值。耳朵在侧面出现、鼻子轮廓换形，必须走“切换 / 可见性通道”，在某个视角范围内整体换掉。切换点附近怎么过渡要单独设计。
5. **L4 修正的作用范围**：一个修正影响多大的视角范围、怎么衰减。Cubism 的做法是“加整行关键点”，我们想要稀疏修正，但要防止修正泄漏到不相关的角度。
6. **模板更新与实例覆盖冲突**：模板删掉了某条被覆盖的曲线时怎么办。

## 5. 检验点（来自 dot，作为验收条件）

1. 统一操作入口不要求撤销一定用逆操作，不可逆和退化变换不能反过来限制编辑能力。
2. 作者数据与求值数据分离之后，保存仍必须覆盖所选资源的引用和局部覆盖，并区分“保存完整工程”和“导出当前结果”。
3. 角度、表情、捏脸共享参数机制，但必须定义作用顺序和覆盖规则：改脸型跨视角生效；当前角度的美术修正不能悄悄改掉角色的固有形状。

## 6. 待 bowen 决定

1. 推荐候选 A 作为 base，B 和 C 的可取之处作为插件或子机制吸收。是否同意这个方向？
2. 参数层顺序 L1 捏形 → L2 视角 → L3 表情 → L4 视角修正，是否符合你的创作直觉？比如表情是否需要按视角分别调整？
3. 使用者能否在角色里**增删**曲线（结构性修改），还是只能调参数和改属性？这决定覆盖机制的复杂度。
4. 纯导航（改视角、选择）是否要进撤销历史？推荐：不进，但撤销时恢复上下文。
5. 产出的“成品线稿”是否需要和源角色保持链接（源更新后它也更新），还是导出即独立？
