## 根因

V0.4.6 在结果安装条件中增加了 `!pending`。持续 orbit 输入令 pending 几乎一直为 true，导致 **计算吞吐没有退化，但已经完成的结果全部被拒绝安装**。

另外两点核实：

1. **V0.4.5 的 Contour 已经是 persistent worker + one active/latest pending**。不能把这次问题归因于“新引入 persistent Contour Worker”。
2. 两版都只在 revision 变化时附带 source，camera-only 本来就没有重发 surface。V0.4.6 的 camera-only 主线程计数只有 contourDispatches，没有任何 geometry 工作。

## 修复后的协议与调度

```ts
{type:'SET_SURFACE', revision, source} // 只在最终 Surface signature 变化时
{type:'RENDER', id, revision, orientation:[qx,qy,qz,qw]} // camera only
```

Worker 在 SET_SURFACE 时从 source + settled Smooth result 建立固定 n24 的 final mesh，并保留它。camera 消息平均约 109 bytes（UTF-8 JSON 表示估算，不声称等于浏览器 structured-clone 内部字节数），不带 vertices、triangles 或 source graph。

- 相机事件只覆盖最新 quaternion；RAF 每个显示帧至多提交一次。
- 加入实际任务耗时驱动的背压：初始预算 32ms，成功后以 0.25 权重追踪 `1.25 × total`，下限 16ms；取消后增加预算。没有假设慢设备必须在固定上限内完成。
- 背压等待期间只有一个最新输入，不保存历史相机队列。3D OrbitControls 本身不节流。
- Worker 的 `LatestJob` 只有一个 active 和一个可替换 pending。新请求使旧 active 的 stale predicate 失效。
- raster 每 512 triangles、flood 每 16,384 visits、边界扫描每 32 rows 提供检查点；累计执行跨过 4ms 后用 MessageChannel 真正让出事件循环，才能收到新消息。单个 chunk 可能超过预算，并非硬实时 4ms 保证。
- projection 后和发布结果前也让出执行。旧请求发现 stale 后停止剩余阶段，不安装旧 revision / 旧已提交 requestId 的结果。
- **过期界限是实际提交的 RAF requestId**。还没有被提交的原始 orbit 输入只覆盖下一次方向，不再像 V0.4.6 那样使所有完成帧失去显示资格。预览自然存在短暂计算延迟，不声称与每一个原始输入事件瞬时同步。

单纯加取消、每 16ms 发一个新任务的实验同样会饥饿：任务需要约 20ms 时，每次都差一点被取消。背压是解决这种问题的必要组成部分，不能只看 discarded/cancelled 数量。

正常测量中不需要大量取消；突发 100 个 worker 请求的测试确认中间 pending 被覆盖、旧 active 被取消、只发布最后 id=100，任务不会排成 100 项队列。

## 计算与 React 范围

- 固定精度保持不变。仅缓存 immutable Contour mesh 的包围盒/半径，消除投影阶段重复 framing。
- raster 保留原来的 half-open / pixel-center 覆盖规则，移除每条扫描线的临时数组。
- flood / trace 规则、洞的处理、union 语义不变；测试对完整头壳四个方向逐像素/逐路径对比冻结的旧版 oracle。
- ContourPanel 不再订阅整个 camera store 来触发 React render；命令式窄 quaternion 订阅只调度 Contour。结果/状态变化仍正常渲染 Contour 自身。
- 3D 卸载时不再额外发布一次低于 OrbitControls change 阈值的阻尼残值，隐藏后稳定保留最后正常发布的 orientation。
- EditView / PatchLayer / LandmarkList / CurvePanel / PatchPanel / OnCurveInspector 仅增加 DEV 计数，不改变行为。

修复后，整个旋转和阻尼收尾阶段，以下计数全部为 0：

`sourceUpdates, dirtyPoints, dirtyCurves, dirtyPatches, pointEvaluations, curveEvaluations, patchEvaluations, patchTessellations, threeBufferRebuilds, threeCurveBufferRebuilds, smoothDispatches`，以及上述六类组件的额外 render。

Project 序列化前后完全相同。关闭 Contour 后旋转不再提交 Contour 工作。源签名变化仍正常更新 mesh / Smooth / Fullness；没有改动它们的数学、拓扑或 persistence。
